# v0.6 Workflow DAGs and Saga Compensation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let clients submit DAG workflows of ordinary jobs that advance atomically in PostgreSQL and run saga compensations in reverse dependency order on failure or cancel.

**Architecture:** New `workflows` / `workflow_steps` tables and workflow link columns on `jobs` (migration 6). A Go engine in `internal/store/postgres` is invoked inside the existing transactions that make a job terminal (`finishJob`, terminal branch of `finalizeFailure`), locks the workflow row, updates step state, dispatches dependents or compensations as new jobs, and settles the workflow status. Pure decision logic lives in `internal/job` and is unit tested; correctness under concurrency and crashes is proven by PostgreSQL integration tests with a shared invariant checker.

**Tech Stack:** Go 1.25, pgx v5, goose v3, PostgreSQL 18, `net/http`, existing NATS outbox (unchanged except trigger payload).

**Spec:** `docs/superpowers/specs/2026-11-08-v0.6-workflows-saga-design.md`

## Global Constraints

- Go module `github.com/Nuryanfa/TaskForge`; Go 1.25.x; **no new Go dependencies**.
- PostgreSQL is the only authority; workflow state never changes from NATS or process memory.
- Public responses and logs never contain step/compensation payloads, `idempotency_key`, execution keys, or `CompensatesExecutionKey`.
- Error codes match `^[A-Z][A-Z0-9_]{0,63}$`. New public HTTP codes: `WORKFLOW_NOT_FOUND`, `WORKFLOW_STATE_CONFLICT`, `WORKFLOW_OWNED_JOB`. New job failure codes: `DEMO_FAILURE`, `DEMO_TRANSIENT`.
- Step name / queue / kind pattern: `^[a-z0-9][a-z0-9._-]{0,63}$`. Label: 1–128 printable characters (`0x20–0x7E`, not only spaces).
- Limits: `TASKFORGE_WORKFLOW_MAX_STEPS` default 32, bounds 1..100; `TASKFORGE_WORKFLOW_MAX_BYTES` default 262144, bounds 1024..4194304; `TASKFORGE_WORKFLOW_PAGE_SIZE` default 50, bounds 1..100.
- Lock order in every workflow transaction: job row(s) → `workflows` row(s) in ascending `id` → `workflow_steps` rows. Queued jobs canceled by the engine during abort are locked with `FOR UPDATE SKIP LOCKED`.
- Workflow statuses: `running, compensating, succeeded, compensated, canceled, compensation_failed`. Step statuses: `pending, dispatched, succeeded, failed, canceled, skipped`. Compensation statuses: `none, waiting, dispatched, succeeded, failed, not_defined`. Abort reasons: `step_failed, canceled`. Job roles: `action, compensation`.
- Every SQL path that changes workflow state has a real-PostgreSQL integration test; integration tests are named `…Integration` and skip without `TASKFORGE_TEST_DATABASE_URL`.
- Run `gofmt -l .` (must print nothing) and `go vet ./...` before every commit.
- Every commit message ends with the trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A step with an unregistered `kind` fails at run time with `UNKNOWN_JOB_KIND`; the workflow must abort and compensate, not hang. → Task 5 test `TestWorkflowUnknownKindAbortsIntegration`.
2. A single-step workflow whose only step fails has nothing to compensate; it must reach `compensated` in the same transaction, not stay `compensating`. → Task 5 test `TestWorkflowFailureWithNothingToCompensateIntegration`.
3. Cancel while every remaining step is already running: the workflow shows `compensating` until those finish, then compensates any that succeeded and ends `canceled`. → Task 6 test `TestWorkflowCancelWhileStepRunningIntegration`.
4. Two concurrent lease-recovery batches touching jobs of the same two workflows in opposite order must not deadlock. → Task 8 test `TestConcurrentRecoveryAcrossWorkflowsNoDeadlockIntegration`.
5. A compensation handler receives the action job's execution key, identical across its retries and crash re-executions. → Task 6 test `TestClaimLoadsWorkflowContextIntegration` and Task 8 crash test.

```go
var ErrWorkflowOwnedJob = errors.New("job belongs to a workflow")
// advanceWorkflows runs the engine for jobs that just became terminal in tx.
// It locks the distinct workflows in ascending id order, then processes each job.
func (s *Store) advanceWorkflows(ctx context.Context, tx pgx.Tx, terminal []terminalJob) error
type terminalJob struct { ID string; WorkflowID *string; StepID *int64; Role *string; Status job.Status; ErrorCode *string }

```

Hook points: `finishJob` calls `advanceWorkflows` with the one job before commit (use `RETURNING workflow_id, workflow_step_id, workflow_role` on its UPDATE). `finalizeFailure` calls it only in the terminal (dead-letter) branch. `RecoverExpiredJobs` collects terminal jobs from the whole batch and calls `advanceWorkflows` once after the loop. `CancelQueuedJob` returns `ErrWorkflowOwnedJob` when the row has a `workflow_id` (check before updating).

Engine behavior is exactly the spec's "Algorithm (pseudo-code)"; `settleWorkflow` loads all steps as `[]job.StepState`, dispatches `job.ReadyCompensations`, then applies `job.Settle` (setting `completed_at`).
