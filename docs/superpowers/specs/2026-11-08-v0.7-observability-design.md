# TaskForge v0.7 design: metrics, connected tracing, dashboards, and SLOs

- Date: 2026-11-08
- Status: Draft for owner review
- Roadmap item: v0.7 "Metrics, tracing, dashboards, and SLOs"
- Builds on: v0.6 (branch `feature/v0.6-workflows-saga`), ADRs 0001–0012

## Intent

Through v0.6 TaskForge can only be observed through JSON logs, the HTTP API,
and the event stream. v0.7 makes it operable with measurable targets:

1. **Connected tracing (the headline).** One job can be followed in Jaeger
   from the HTTP request that submitted it, through PostgreSQL, to every
   attempt a worker made, and onward through the workflow steps and
   compensations it caused. The trace context crosses process boundaries
   **through the database**, which is rare and is the case-study material.
2. **Defined SLOs.** SLIs are written down before any dashboard exists,
   measured from database timestamps, and protected by burn-rate alerts.
3. **A "what is broken?" dashboard** and core metrics.

Audience (unchanged from v0.6): backend/system-design interviewers. They
judge evidence, so v0.7 ships tests that prove span relationships, a test that
jobs still run when the trace exporter is down, rule unit tests for the SLO
alerts, and a demo that deliberately violates an SLO.

## Owner decisions

| # | Topic | Decision |
| --- | --- | --- |
| 1 | Stack | Prometheus metrics (`/metrics`), OpenTelemetry tracing exported over OTLP to Jaeger, Grafana with provisioned dashboards, Prometheus rules for SLOs. All in Compose. |
| 2 | Trace propagation | Trace context travels with the job: a W3C `traceparent` string is stored in a **nullable** column (migration 7). |
| 3 | Delayed work | Span **links**, not parent-child, for work that was not ready when enqueued (delayed and cron jobs); one rule, recorded in an ADR. Every attempt gets its own span with the attempt number; workflows connect their steps and compensations to the workflow submission. |
| 4 | SLIs | Start latency is measured from the moment a job became **ready** (`available_at`), not from submission. Only **platform** errors burn the reliability budget; handler failures (for example `demo.fail`) do not. SLIs are defined in the docs before dashboards. |
| 5 | Cardinality | Job IDs and workflow IDs are span attributes only, never metric labels. The `kind` label is limited to registered kinds. |
| 6 | Out of scope | Trace propagation through the outbox and NATS. |
| 7 | Evidence | An integration test asserting span relationships with an in-memory exporter; a test that jobs run with the OTLP exporter down; a demo that triggers an SLO burn-rate alert, with screenshots for the portfolio. |

## Goals

- A submitted job's attempts appear in the same trace as its submission, or
  linked to it when the job was not ready immediately.
- Workflow steps and compensations appear causally: a step's attempt is a
  child of the attempt (or request) whose transaction dispatched it.
- Observability is optional and failure-isolated: with tracing disabled,
  misconfigured, or Jaeger down, jobs run exactly as in v0.6, and exporting
  never blocks a request or a job beyond a small bounded cost.
- Metric label sets are bounded by configuration, not by client input.
- SLIs are computed only from PostgreSQL timestamps (no host clock skew; see
  ADR 0011's lesson).
- No payloads, results, idempotency keys, execution keys, or credentials in
  spans, metric labels, or logs.

## Non-goals

- Trace propagation through the outbox / NATS events (owner decision 6).
- Log shipping, log-trace correlation beyond adding `trace_id` to existing
  error logs (see "Calls").
- Alertmanager routing (email, Slack, paging). Alerts are visible in
  Prometheus and Grafana only.
- Per-tenant SLOs, long-term metric storage, exemplars.
- Profiling (pprof endpoints).

## Anti-goals (a failure even if it "works")

- A job that fails, stalls, or slows noticeably because the trace exporter or
  Prometheus is unavailable.
- A metric label whose values come from client input without a bound (job ID,
  arbitrary queue name, arbitrary kind).
- A start-latency SLI that delayed or cron jobs violate by design.
- A reliability SLI that `demo.fail` (a deliberate handler failure) consumes.
- A trace for a delayed job that spans days as one parent-child tree.
- Any payload, key, or DSN in telemetry.

## Tracing design

### Storage (migration `000007_add_trace_context.sql`)

```sql
ALTER TABLE jobs ADD COLUMN trace_parent TEXT
    CHECK (trace_parent IS NULL OR trace_parent ~ '^00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}$');
-- Decided once at enqueue: TRUE when the job was not ready at creation
-- (client run_at / delay_seconds in the future), so attempts link instead of
-- parenting. Retry backoff later moves available_at but must not flip this.
ALTER TABLE jobs ADD COLUMN trace_link BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE workflows ADD COLUMN trace_parent TEXT
    CHECK (trace_parent IS NULL OR trace_parent ~ '^00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}$');
```

`trace_parent` is the W3C `traceparent` of the span that **caused** the row
to exist. It is never returned by the public API (it is harmless, but the API
surface stays unchanged) and never put in outbox payloads (decision 6).
`tracestate` and baggage are not stored.

### Span model

| Span | Process | Kind | Parent / link | Key attributes |
| --- | --- | --- | --- | --- |
| HTTP server span per request | API | server | incoming `traceparent` header if present | `http.route` (pattern, not path), status |
| `job.enqueue` | API | producer | child of HTTP span | `taskforge.job.id`, `kind`, `queue`, `delayed` |
| `workflow.submit` | API | producer | child of HTTP span | `taskforge.workflow.id`, `step_count` |
| `job.attempt` | worker | consumer | **see rule below** | `taskforge.job.id`, `kind`, `queue`, `attempt`, `max_attempts`, `workflow.id`, `workflow.step`, `workflow.role`, outcome, error code |
| `workflow.dispatch` (event on the attempt span, not a span) | worker | — | — | names of dispatched steps / compensations |
| `schedule.dispatch` | worker | internal | new root per dispatch batch | `schedule.id`, `scheduled_for` |
| `lease.recovery` | worker | internal | new root per batch with work | `recovered`, `failed` |
| `job.redrive`, `workflow.cancel` | API | internal | child of HTTP span | ids |

**The parent/link rule (ADR 0013):**

- The `trace_parent` stored on a job is the span context of whatever caused
  it: the `job.enqueue` span, the `workflow.submit` span, the attempt span
  whose transaction dispatched it (workflow engine), the `workflow.cancel` or
  `lease.recovery` span that triggered compensations, the `job.redrive` span,
  or the `schedule.dispatch` span.
- A `job.attempt` span is a **child** of the stored context when
  `trace_link` is false: immediate jobs, workflow steps, compensations,
  redrives, and cron-materialized jobs.
- It is a **new root span with a link** to the stored context when
  `trace_link` is true, which the API sets when a job is submitted with
  `run_at` / `delay_seconds` in the future. A delayed job therefore never
  stretches one trace across hours or days. The flag is fixed at creation:
  retry backoff moves `available_at` but never changes the rule.
- Retries stay in the job's trace: attempt 2 is a sibling of attempt 1 (same
  parent), carrying its attempt number. Backoff is bounded (max 30 minutes),
  so the trace length stays bounded and the gap shows backoff honestly.
- A job with no stored context (created before migration 7, or tracing
  disabled when it was created) gets a new root attempt span.
- Fan-in: a workflow step dispatched when its last dependency completed is a
  child of that last dependency's attempt span; the other dependencies are
  added as span links when their attempt contexts are known (best effort; the
  builder may store dependency job ids instead of contexts). Builder's call
  how far to go; the parent rule is mandatory, links are nice-to-have.

**Context plumbing.** The worker deliberately runs handlers and persists
outcomes on contexts derived from `context.Background()` (so shutdown does not
abort them). The attempt span context must therefore be attached explicitly
(`trace.ContextWithSpanContext`) to the execution and persistence contexts.
`CompleteJob` / `FailJob` read the span context from their `ctx` and the
engine stamps it as `trace_parent` on every job it dispatches in that
transaction. Recovery and cancel do the same with their own spans. The store
must not import exporter packages; it only reads a span context from `ctx`
and formats it with the W3C propagator.

**Handler access.** Handlers receive the attempt span in their `ctx`, so a
handler that calls an instrumented downstream propagates the trace for free.
Nothing in `job.Execution` changes.

### Exporter, sampling, failure isolation

- Tracing is enabled only when `TASKFORGE_OTEL_ENDPOINT` is set (OTLP over
  HTTP, e.g. `http://jaeger:4318`). Unset → no-op tracer and no exporter; no
  valid span context exists, so `trace_parent` stays NULL and attempts start
  new (unexported) roots.
- Batch span processor with bounded queue (default 2048) and drop-on-full;
  export timeout bounded (default 5 s); shutdown flush bounded by the existing
  shutdown timeout.
- Sampling: parent-based, root ratio `TASKFORGE_OTEL_SAMPLE_RATIO` (default
  `1.0`). A sampled-out context still propagates (`traceparent` flags `00`).
- Exporter errors are counted (`taskforge_otel_export_failures_total`) and
  logged at most once per minute; they never fail a request or job.

## Metrics design

Every process exposes Prometheus metrics:

| Process | Endpoint |
| --- | --- |
| API | `GET /metrics` on the existing HTTP server |
| worker | new listener `TASKFORGE_METRICS_ADDR` (default `127.0.0.1:9091`), `/metrics` only |
| relay | same variable (default `127.0.0.1:9092`) |

### Label bounding

- `kind`: one of the registered kinds (`demo.echo`, `demo.fail`,
  `demo.flaky`, `demo.sleep`), otherwise `other`. The API does not import the
  worker; the list of registered kinds lives in one shared place (builder
  chooses, e.g. `internal/job` constant set the registry is checked against by
  a test).
- `queue`: kept only if listed in `TASKFORGE_METRICS_QUEUES` (default
  `default`), otherwise `other`.
- `route`: the `net/http` mux pattern (e.g. `POST /v1/jobs/{id}/cancel`), never
  the raw path.
- `outcome`, `class`, `status`: fixed enums.

### Core metrics (names are the contract; the builder may add more)

| Metric | Type | Labels | Source |
| --- | --- | --- | --- |
| `taskforge_http_requests_total` | counter | route, code | API |
| `taskforge_http_request_duration_seconds` | histogram | route | API |
| `taskforge_jobs_submitted_total` | counter | queue, kind, delayed | API (new jobs only, not idempotent replays) |
| `taskforge_job_start_delay_seconds` | histogram | queue, kind | worker, at claim: `started_at − available_at`, both from the claim statement's DB clock |
| `taskforge_job_attempt_duration_seconds` | histogram | kind, outcome | worker |
| `taskforge_job_outcomes_total` | counter | kind, outcome (`succeeded`, `retry_scheduled`, `dead_lettered`, `abandoned`), class (`platform`, `handler`, `none`) | worker for its own outcomes; recovery reports per-outcome counts (abandoned → retry or dead-letter, class `platform`) |
| `taskforge_jobs` | gauge | state (`ready`, `delayed`, `running`, `expired_lease`) | DB collector |
| `taskforge_dead_letters_unredriven` | gauge | — | DB collector |
| `taskforge_outbox_oldest_unpublished_age_seconds` | gauge | — | DB collector |
| `taskforge_workflows` | gauge | status (non-terminal) | DB collector |
| `taskforge_workflow_completions_total` | counter | status (terminal) | the store reports workflows it settled in a transaction; the calling process increments after commit |
| `taskforge_lease_recoveries_total` | counter | result (`recovered`, `failed`) | worker |
| `taskforge_otel_export_failures_total` | counter | — | all |
| Go runtime and `pgxpool` stats | standard collectors | — | all |

**DB collector:** runs in the API process only, refreshes every
`TASKFORGE_METRICS_DB_REFRESH` (default 15 s) with one bounded, indexed query
per gauge under the normal query timeout, and serves cached values on scrape
(a scrape never queries the database). With several API replicas, dashboards
use `max()` across instances.

**Classification of failures (SLI-relevant, decision 4):**

| Class | Codes |
| --- | --- |
| `platform` | `LEASE_EXPIRED`, `SHUTDOWN_TIMEOUT`, `UNKNOWN_JOB_KIND` |
| `handler` | every other failure code (`DEMO_FAILURE`, `INVALID_JOB_PAYLOAD`, `EXECUTION_TIMEOUT`, `INVALID_JOB_RESULT`, …) |

`EXECUTION_TIMEOUT` is a handler class: a slow handler or downstream is the
handler owner's budget, not the platform's. `UNKNOWN_JOB_KIND` is platform: it
means the deployment does not run a handler that clients use.

## SLOs

Defined in `docs/SLO.md` (new) before the dashboard; expressed as Prometheus
recording and alerting rules in `deployments/prometheus/`.

| SLO | SLI (good / valid) | Target | Window |
| --- | --- | --- | --- |
| **Start latency** | jobs whose `start_delay` (ready → claimed) ≤ 5 s / all claimed jobs | 99 % | 28 days |
| **Reliability** | terminal outcomes that are not a `platform` dead-letter / all terminal outcomes (`succeeded` + `dead_lettered` of any class; `canceled` excluded) | 99.5 % | 28 days |
| **API availability** | non-5xx responses / all responses, excluding `/healthz`, `/readyz`, `/metrics` | 99.9 % | 28 days |

`start_delay` uses `available_at`, so delayed jobs, cron slots, retry
backoff, and workflow dispatch time are all measured from readiness, never
from submission. The 5 s bucket must be an explicit histogram boundary.

**Alerts:** multi-window, multi-burn-rate per SLO (page-level: 14.4× over
1 h and 5 m; ticket-level: 6× over 6 h and 30 m), as Prometheus rules with
`promtool test rules` unit tests that prove each alert fires on a synthetic
burn and stays silent at budget-neutral load.

## Dashboard

One provisioned Grafana dashboard, "TaskForge — what is broken?", top to
bottom:

1. SLO status row: current SLI vs target and error budget remaining for the
   three SLOs, plus firing alerts.
2. Work in the system: `taskforge_jobs` by state, DLQ size, outbox lag,
   non-terminal workflows.
3. Latency: start delay p50/p95/p99 vs the 5 s line; attempt duration by kind.
4. Failures: outcomes by class and kind, recoveries, export failures.
5. API: request rate, 5xx ratio, latency by route.

Each panel answers one question in its title ("Are jobs starting on time?").
Grafana gets a Jaeger data source so operators can jump from a slow panel to
traces (manual search by service and time range; exemplars are a non-goal).

## Deployment

Compose adds `prometheus`, `grafana`, and `jaeger` (all-in-one with OTLP),
all bound to loopback, with provisioned configuration under
`deployments/` (prometheus.yml, rules, grafana datasources and dashboard
JSON). API, worker, and relay get `TASKFORGE_OTEL_ENDPOINT` and metrics
addresses. Image versions pinned. Grafana anonymous viewer on loopback only.

## Demo: making an SLO burn

`cmd/taskforge-loadgen` (new, small): submits a configurable mix of
`demo.echo`, `demo.flaky`, `demo.fail`, and `demo.sleep` jobs (and optionally
workflows) at a fixed rate against the API. `docs/SLO.md` gets a "burn the
budget" walkthrough: run loadgen with long `demo.sleep` jobs while the worker
runs with `TASKFORGE_WORKER_CONCURRENCY=1`, watch start delay cross 5 s, the
fast-burn alert fire, and the dashboard turn red; then follow a slow job in
Jaeger. The walkthrough names where to take the portfolio screenshots. The
demo uses short evaluation windows via a Compose override so it fires in
minutes rather than an hour.

## Testing (evidence)

- **Span relationships (integration, in-memory exporter, real PostgreSQL,
  no Jaeger):**
  - immediate job: HTTP → `job.enqueue` → `job.attempt` all in one trace,
    attempt is a child of enqueue;
  - retried job: two attempt spans, siblings, attempt numbers 1 and 2;
  - delayed job: attempt span is a new root with a link to the enqueue span;
  - workflow: step B's attempt is a child of step A's attempt; compensation
    attempts are children of the span whose transaction dispatched them;
  - recovered job: the retry after lease expiry is a child of the stored
    context and the `lease.recovery` span records the recovery;
  - job created with tracing disabled has NULL `trace_parent` and still runs.
- **Exporter down:** tracing enabled against a closed port; a job and a
  workflow complete within the normal bound; worker shutdown stays within its
  timeout; `taskforge_otel_export_failures_total` increases.
- **Metrics:** scrape `/metrics` of each process after activity; assert the
  core series exist; assert no label value equals a job ID, workflow ID, or
  an unlisted queue/kind (bounded-cardinality test with a random kind and
  queue submitted); start-delay histogram has a 5 s boundary.
- **SLI correctness:** a delayed job and a retry with backoff record
  `start_delay` near zero, not their delay; `demo.fail` dead-letters with
  class `handler`; a lease-expiry dead-letter has class `platform`.
- **Rules:** `promtool test rules` for every alert (fires on burn, silent
  otherwise); `promtool check rules` and a Grafana dashboard JSON lint in CI.
- **Migration 7** upgrade test from v0.6 with live data.
- Existing v0.1–v0.6 suites, including the workflow soak, stay green with
  tracing enabled against an in-memory exporter.

## Dependencies

New Go modules (versions must support Go 1.25; the builder pins the newest
compatible releases, as v0.5 did for NATS): `github.com/prometheus/client_golang`,
`go.opentelemetry.io/otel` (+ `sdk`, `trace`,

## Implementation order (suggested)

1. Migration 7 + upgrade test; `trace_parent` read/write in the store.
2. `internal/telemetry`: tracer provider setup (noop / OTLP / test exporter),
   propagation helpers, metrics registry and label bounding.
3. API: HTTP middleware (spans + metrics), `job.enqueue` / `workflow.submit`
   / redrive / cancel spans, `trace_parent` stamped on create, `/metrics`, DB
   collector.
4. Worker: attempt spans with the parent/link rule, context plumbing into
   execution and persistence, engine stamping dispatched jobs, recovery and
   schedule spans, worker metrics and listener; relay metrics.
5. Span-relationship, exporter-down, metrics, and SLI tests.
6. Prometheus rules + `promtool` tests; Grafana provisioning and dashboard;
   Compose services; CI steps.
7. Loadgen + burn demo; docs and ADR.

## Calls made by the builder (owner: please check)

- Attempt spans are children of the stored context unless the job was
  client-delayed (`trace_link`, decided at enqueue), in which case they are new
  roots with a link; retries stay in the job's trace as siblings.
- `trace_link` is a second column in migration 7, so retry backoff cannot
  flip the parent/link rule.
- Workflow steps and compensations are children of the attempt (or
  request/recovery span) whose transaction dispatched them, which gives a
  causal chain; other fan-in dependencies are optional links.
- `trace_parent` is not exposed by the API and not added to outbox events.
- OTLP over HTTP (not gRPC) to keep dependencies light.
- DB-state gauges are collected only in the API process, cached, never on the
  scrape path.
- `EXECUTION_TIMEOUT` counts as a handler failure; `UNKNOWN_JOB_KIND`,
  `LEASE_EXPIRED`, and `SHUTDOWN_TIMEOUT` count as platform failures.
- SLO targets 99 % / 5 s start latency, 99.5 % reliability, 99.9 % API
  availability, 28-day windows; Google SRE multi-window burn rates.
- No Alertmanager; a new `cmd/taskforge-loadgen` tool drives the demo.
- Error logs gain a `trace_id` field when a span is active (IDs only).
